# 输出格式重复重试的原因与修复

本次针对正在运行的网络触达单组实验进行工程修复。保持全部研究输入、提示词、模型请求选项、11项条件内容、评分、评论和转发规则不变，不另开独立条件。

## 已查明的实际原因

暂停实验 `government-rumor-v6-openai-20261023-015236-672409` 已完成前2轮。第三轮A0143的四份回答都包含11项应用说明，输出也没有被截断，但把程序给定的 `e5aa58ede34ae2f5` 写成了 `eaa58ede34ae2f5`，少了一个字符。此前校验把这当作整份判断无效，反复请求同一输入仍然抄错，最终暂停。

另有回答将 `source_trust` 写为同义字段 `source_prior`，或将 `mbti_preferences` 写为 `mbti`，以及在完整11项之外附加补充说明。这些也曾触发过格式重试。因此这个问题不是额度用尽，也不是需要继续加大输出token。

## 现在如何处理

- 运行标识由程序依据当前实际观察计算并绑定。它是工程关联信息，不用LLM抄写能力来判定11项个人条件是否存在。模型原样返回的错误标识仍保留。
- 只支持明确的字段同义映射：source_prior→source_trust、government_prior→government_trust、mbti→mbti_preferences。若两种字段同时出现且内容不同，仍拒绝，不能偷偷择一。
- 11项规定的说明必须全部实际存在，并通过原来的作用对象和4—60字符摘要校验。缺少条件、空白或无效摘要仍失败；程序不会补写任何个人条件应用说明。
- 已有完整11项以外的补充说明保留在supplementary_condition_application中，API原文也保留，不因多写补充说明否定完整11项。
- 分数、分项评分、评论、转发、证据ID均不由格式适配器修改；JSON语法错误和不可见证据引用仍被拒绝，不从文字里猜测重建答案。
- 所有格式适配记录在output_format_repairs中。API逐字原文仍在审计目录的request-*.json；动作中的raw_answer是交给引擎的解析/适配对象，不能将它当作API逐字原文。

已有成功缓存优先使用，不回头选择更早或分数更高的答案。对于没有成功缓存的决策，仍按请求历史顺序采用第一份可合法解释的完整回答，不按相信程度挑选。

## 本次保留进度的核对

修复前保存源码备份和父实验快照。离线重放前2轮，逐一核对259份历史请求的Prompt和请求签名，全部不变；241份已有成功缓存的答案也全部相同。A0143可以直接使用请求250中已有的22分回答，只修正关联标识，不必再次请求该用户。

本次恢复使用仅针对该父实验的精确迁移清单：核对旧/新源码哈希、未改变的提示词函数、全部原始请求、成功缓存、预算账本和完整检查点。研究模型/环境源码、素材、配置和累计预算均不得改变。普通断点恢复仍保持同版本检查，并不开放任意跨版本续跑。

若以后再次出现真正的格式不合格，validation文件会记录invalid_json、条件覆盖/摘要问题、不可见证据等具体类别。不要将所有Format retry都理解为API限流，也不要为此不断提高token或无限按R。

本修复不解除65536代理token的输入保护。后续评论增长如再次达到输入上限，应单独在L菜单决定是否调整；这与本次字段格式问题是两类原因。
