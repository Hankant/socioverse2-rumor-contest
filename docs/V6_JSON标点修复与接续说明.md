# V6：JSON标点修复与原实验接续

截图对应父实验 government-rumor-v6-openai-20261023-152542-068585，已完成1轮，81次API请求、67份有效回答，因A0036第2轮连续4次格式失败暂停。

## 实际原因

不是上下文超限或输出token不足。供应商返回finish_reason=stop，正文存在根对象提前关闭后又追加condition_context_ref、多余末尾逗号，另有一次缺少comment对象闭括号。部分回答还猜出了不可见的C00评论编号。原程序把这些情况整体归为格式错误，有限重试仍重复相同错误。

## 处理

- 新syntax_repair只允许最多3处确定的分隔符修复：删除多余根闭括号、尾逗号，或在文本结束补齐已完整字段的闭括号。
- 引号字符串、字段名、数字、布尔值、null及其顺序必须与原始响应逐字一致；不能补分数、评论、行为、条件说明，不能替换证据ID。
- 修复后须包含完整所需根字段，动作对象结构明确，并通过原来的全部评分、可见性、11项说明和MBTI评论应用校验。重复字段、额外文本、缺失内容或嵌套含糊时不接受，仍有限重试。
- finish_reason=length、空响应和供应商拒绝不作为完整回答修复。
- 原raw_response始终保留，接受的回答另有output_syntax_repairs，记录编辑类型、原/修复后哈希、literal_sequence_unchanged和behavioral_fields_changed=false。

## 提示结构与证据编号

机器协议加入可解析的完整JSON结构模板；context_ref放在前部、condition_application最后，明确所有评分和行动由角色自行决定。null及空数组只是待填占位，不是默认评分或行动。输出仍保留11项简短应用摘要，不索取长篇推理。

评论表现在显式显示comment_id，避免让模型自行套编号。不可见证据重试时提供从相同已见材料生成的准确ID清单，不增加未来内容，也不放宽引用校验。

## 旧回答与选择顺序

原67份有效缓存优先复用并保持哈希不变。A0041已有第81次请求的有效回答，仍使用该缓存，不被更早的可修复回答替换。

A0036没有有效缓存，按原请求顺序检查：72号虽可修括号，但仍含无效证据，不接受；75号删除一个提前闭合的括号后全校验通过，复用其原分数51及原评论/转发选择。程序不按分数高低挑选回答。76号结构含糊不接受；更晚的79号即使也可修复，也不替换已找到的首个有效回答。
