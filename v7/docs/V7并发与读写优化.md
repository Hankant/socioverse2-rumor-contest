# V7 并发与本地读写优化（2026-10-26）

实验条件、300名用户、网络、提示词、评论和记忆规则、模型、执行预算均保持原值。API继续采用主Key最多4路、三个副Key各最多1路，总上限7路。失败Key仍单独冷却，按已配置的600秒间隔恢复探测。

## 改动

1. 调试事件使用独立的日志锁和按行刷新的文件流，不再逐条调用磁盘同步屏障。关闭客户端时同步日志。预算、原始请求、原始回答、有效缓存、检查点和Key冷却状态仍通过原来的原子替换及同步机制保存。
2. 有效缓存命中时，仅检查历史索引及有效回答，不读取包含重复完整提示词的原始请求JSON；未解决的请求仍从原始审计文件核验，未知结果保护保持生效。
3. 原始回答持久保存后，释放全局请求通道，再进行语法修复、条件校验和有效缓存写入。发送前的预算预留和未知请求保护仍在。
4. 活跃槽位、排队数量等运行计数采用原子更新，取消逐计数的磁盘同步；这些计数在启动时重建。它们不替代付费请求账本。
5. 健康Key成功时不重复同步未变化的冷却文件；恢复探测成功、失败和冷却变化仍持久保存。
6. 同一受独占控制器保护的批任务恢复时，继续使用本组已有审计目录，避免重新复制或创建十几万份请求与缓存的硬链接。新运行仍使用独立结果目录和溯源文件，记录 `exclusive_batch_reuse_v1`。历史有效缓存继续复用，累计预算持续增长。
7. 合作暂停时，不再额外扫描所有历史提示词。原始回答保存、检查点与结果导出仍保留。
8. 每组DuckDB限制为1个数据库工作线程和256MB缓冲预算；大型Parquet及最终CSV导出依次执行。此限制只影响执行资源，不调整用户人数、决策或结果口径。
9. 检查点加载和历史状态重放最多同时进行2组，避免机械硬盘上几十个大文件交叉读取。各组到达原完整轮次后立即释放恢复许可，继续加入原有7路API请求池。54个实验仍独立排队推进。

## 恢复边界

运行代码发生维护变更时，仍必须通过固定源文件哈希的维护清单核验。清单同时要求科学输入、配置、模型、步数和预算不变。已完成的组跳过；已完成回合按检查点重放，不重复调用API。

槽位计数表示已获准的任务数量。真实HTTP活动应依据 `http_dispatch` 与 `response_body_received` / `request_error` 配对计算，不能单凭槽位峰值宣称持续跑满7路。
