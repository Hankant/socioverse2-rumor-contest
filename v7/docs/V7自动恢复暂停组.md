# 暂停实验组继续使用可用API

2026-10-25用户要求恢复6个暂停组，并按可用API继续调用。核对实际记录后，4组共有5次已发送请求发生ReadTimeout，1组达到输出校验重试上限，另1组收到HTTP422。此维护不改变模型、prompt、人口、网络、实验参数或预算；仅增加批次恢复调度和登记本次补做授权。

本次恢复只补做缺失或未通过校验的决策。每组已成功保存的回答继续复用，完整轮次从检查点恢复；原API请求和累计预算保留。90秒超时后没有收到完整答案的5次调用可能已经计费，重新发送可能再次计费。重发授权记录精确到请求文件、逻辑prompt哈希、用户和轮次。

正常API调度继续遵守限流后的5路上限：主API最多2路，三个副API各最多1路；冷却中的API不会被当作可用容量。恢复任务进入同一个共享队列，根据哪个API可用且有空位分配，不固定到某个副API；如果当前只有主API可用，就通过主API推进。

自动恢复策略保存在当前批次request_controls.json的automatic_recovery。已记录明确的用户授权；同一逻辑决策的网络结果缺失最多自动补发3次；同一决策的输出校验失败最多额外开启2个生成窗口，每个窗口仍遵守冻结配置中的format_max_attempts=4。两类自动恢复开始前等待30秒，恢复次数跨重启保留。每次恢复都复制原审计、保留原请求和缓存，不重置任何额度累计；只有通过原有校验的回答才计入结果。

自动恢复仅覆盖有明确APITimeoutError/APIConnectionError记录的未知结果，以及可重试的输出协议错误。供应商明确拒绝生成、输入或累计预算上限、用户主动暂停、文件导出失败，以及一般程序错误和HTTP422不会被无限重试。本次已有的422由用户指令单独登记一次恢复授权，重新进入可用API队列；如果再次出现，需要查看具体接口诊断。

该功能在批次工作线程内恢复本组，其他实验组继续运行。失败次数达到有限上限时保留准确暂停状态，不生成虚假结果，不放宽证据ID或评分校验。

恢复性能：原始request-*.json和response_cache中的不可变JSON在同一NTFS卷使用硬链接复用，跨卷或不支持时回退普通复制；预算、限流状态、恢复授权和追加事件日志保持独立副本。所有程序JSON更新使用原子替换，即使更新子目录也不会覆盖原目录记录。原始审计视作只读。此优化不改变逻辑请求、评分或缓存内容。

2026-10-25账号升级后，用户要求主API再增加一路：正常总并发6路（主3、三个副API各1），再次遇到限流则保存为5路（主2、其余各1）；失败API仍每600秒使用真实待处理决策测试恢复。显式恢复命令recovery_probe_request带唯一id、待测slots和用户授权，可让升级后的账号提前测试；同一命令跨重启只执行一次，未结束的请求不会被取消。每个API容量和恢复命令支持运行中读取request_controls.json，调度变更不需要重启54组。

每组的请求、预算和审计采用本组RLock保护，避免一组恢复历史时阻塞其他组HTTP回调。历史索引优先使用已保存request_start事件中的请求号及prompt哈希定位，读取当前决策需要的原始JSON并核对哈希；没有事件对应的旧记录仍完整读取。内存索引不复制prompt/base_prompt大文本，原始审计文件保留全部内容；raw_response、状态、重试次数和所有预算字段照常使用。这些是恢复读写优化，不修改发给模型的内容，也不放宽回答校验。
