# V7共享6路API请求分配

2026-10-24按用户要求变更现有54组批次的运行调度。全局最多6个API请求同时执行，其中主API最多3个，其余三个API各最多1个。容量共享于54组，不是每组6个。分配按3:1:1:1加权轮流选择，并检查每个API的在途数；请求耗时不同时，实际调用次数比例不必恰好3:1:1:1。

后续增加自动降档：遇到明确的HTTP 429/529或供应商限流错误码时，保存全局上限5、主API上限2、其余三个API上限各1。已发出的响应正常等待并保存；不取消在途请求，待它们返回后按新上限放行。历史峰值可能仍为6或主API为3，这表示降档前的运行记录。降档持续生效，普通重启或接口恢复不自动升回6路；如需升回6路，由用户另行调整。余额不足、服务错误、无效参数和结果未知不会单独触发这个并发降档。

某个API明确返回限流、余额不足等可切换错误时，仅该API进入600秒冷却；同一任务在其他有空位的API继续。其他API仍遵守各自的3/1/1/1上限，容量不足时排队，不擅自增加并发。供应商Retry-After超过600秒时，遵守更长时间。模型、prompt、温度、人口、网络、实验参数、预算和已保存答案不变。

冷却期结束后，用一条正在排队的正常Agent决策作为恢复测试，每个冷却API同时只允许一个恢复测试。成功后恢复该API的正常容量；再次明确失败后重新冷却600秒。没有单独收费的空闲健康检查；等待恢复时不预留新请求预算。即使所有API暂时不可用，也保留当前运行和缓存等待，不反复复制整组运行。没有待办任务时，不额外调用接口。

读取超时导致结果未知、无效模型/参数、输入或累计预算上限等继续使用原有保护；不会伪造答案、重置预算，或擅自补发结果未知的请求。

配置位于当前批次的request_controls.json：max_global_concurrency=6；api_slot_concurrency为primary=3、backup=1、third=1、fourth=1；api_retry_interval_seconds=600。全局上限可热更新；每个API的容量和恢复间隔在本次维护重启后加载。api-capacity-state.json显示各API实际在途数、峰值、冷却截止时间和恢复测试状态；global-request-state.json还包含进入全局调度但可能等待API空位的任务数，不能把它全部当成已经发出的HTTP请求。

自动降档配置rate_limit_fallback为max_global_concurrency=5，api_slot_concurrency为primary=2、backup=1、third=1、fourth=1。触发后rate_limit_fallback_active为true，request_controls.json及容量状态均反映实际限制。限流API仍冷却600秒，其冷却期间实际可用容量会低于5，不能把已拒绝请求的接口强行计入5路可用容量。

启动：双击项目根目录的Run-V7-Batch54.cmd；安全暂停：双击Pause-V7-Batch54.cmd，等待在途响应保存后再关闭窗口。已有结果保存在原Results_V7目录，完整检查点与有效回答缓存继续复用。
